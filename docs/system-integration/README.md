## 一、模块定位

本目录归档「**系统集成与交互体验**」模块的全部设计交付物。

在「AI Fiction Navigator · 网络小说智能推荐系统」四人小组中，本模块不负责任何单一业务能力（趋势、搜索、舆情各有专人），而是承担**让三个独立模块协同运转为一个完整系统**的工程职责。具体包括：

- **数据骨架**：统一全模块共用的数据模型，作为跨模块协作的"普通话"
- **接口契约**：定义所有模块对外暴露的 API 规范，作为跨模块通信的"协议层"
- **中央编排**：实现 Router Agent，把用户的自然语言请求路由到正确的下游模块
- **运维监控**：建立月度对账机制，让系统的稳定性、成本、用户行为可被持续观测
- **前端交互**：提供用户与系统对话的统一入口（聊天界面 + 大屏 + 详情页）

## 二、设计哲学

### 2.1 我对"系统集成"的理解

在 AI 应用的工程实践中，"集成"往往被低估为"把别人的东西拼起来"的体力活。但本项目的实际情况是：**三位组员各自负责端到端的垂直模块，谁都不天然关心"整体如何对外呈现为一个产品"**。如果集成端不主动定义标准、约束接口、串联流程，最终会出现三个互不兼容的"半成品"。

因此我把自己的角色定位为：

- **不是搬运工**，而是**协议制定者**
- **不是补丁工**，而是**架构守门人**
- **不是事后整合**，而是**前置设计**

这也是为什么我交付的不是代码，而是 **5 份设计文档**——因为没有前置的契约共识，任何代码集成都会变成扯皮现场。

### 2.2 三条贯穿全部文档的核心原则

- **数据契约优于代码实现**  
  所有模块必须先就数据结构、接口协议达成共识，再独立编码。文档先行，代码跟随。

- **解耦优于聚合**  
  任何单一模块的故障**不得**导致整个系统不可用。每个调用链路都必须有明确的降级路径与兜底策略。

- **可观测性是产品的一部分**  
  Token 消耗、模块延迟、Fallback 触发率，这些不是运维内部数据，而是系统对自身的承诺。如果数不出来，就说明做得不够好。

### 2.3 为什么文档比代码先行

本项目的客观约束是：

- 四人并行开发，不存在"等一个人写完再写另一个"的串行空间
- 每个模块的负责人技术栈、习惯、工具偏好各异
- 教学项目时间窗短，返工成本极高

所以我选择用**前置文档**的方式锁定接口、数据、流程，让三位组员可以**真正独立、并行**地推进自己的模块，而不会到了联调阶段才发现"你的输出我读不懂"。

## 三、交付物清单与阅读顺序

本模块共交付 **4 份核心文档** + 本导航文档。建议按以下顺序阅读：

### 📘 1. `unified-data-model-sql.md` —— 数据骨架

**核心问题：** 系统有哪些数据？这些数据怎么组织？

**核心内容：**
- 8 张核心数据表的 PostgreSQL DDL（小说、趋势指标、舆情评分、原始评论、向量索引、用户画像、会话日志、Token 日志）
- 各表的字段定义、索引策略、外键约束
- 跨模块数据流转的所有权约定（谁写、谁读、谁删）

**为什么先读这份：** 数据模型是整个系统的地基。理解了数据怎么流动，才能理解后续接口与编排的设计动机。

---

### 📗 2. `system-openapi-v1.0.md` —— 接口契约

**核心问题：** 各模块之间如何对话？前端如何调用后端？

**核心内容：**
- 基于 OpenAPI 3.0 规范的全局 API 定义
- 13 个核心接口，覆盖趋势 / 搜索 / 舆情 / 集成 4 大模块
- 统一响应封装、错误码、分页、限流、降级策略
- Mock 接口规范（含金标测试数据约定）
- JSON Schema 强校验定义
- 接口归属责任矩阵

**为什么第二个读：** 数据模型回答"系统有什么"，接口契约回答"模块怎么用"。这是连接数据层与应用层的桥梁。

---

### 📕 3. `router-agent-workflow.md` —— 编排逻辑

**核心问题：** 用户的一句话，如何被系统理解并响应？

**核心内容：**
- 基于 LangGraph 的状态机设计（9 节点 + 4 意图分支）
- 完整的 AgentState 数据结构定义
- 每个节点的输入、输出、超时、降级策略
- 与下游模块的契约约定（如何调用、如何处理失败）
- 4 个典型场景的端到端流转案例
- LangGraph 工程实现代码骨架

**为什么第三个读：** 数据与接口都准备好后，这份文档讲的是"系统的大脑如何思考"。这是本模块技术含量最高的一份。

---

### 📙 4. `ops-monthly-report-template.md` —— 运维对账

**核心问题：** 系统跑得好不好？成本花在哪里？哪个模块拖后腿？

**核心内容：**
- 月度运维报告的标准化模板
- 5 个核心 KPI（可用率、延迟、Fallback 率、成本等）
- 4 个模块的分项监控指标
- Token 成本审计（按模块、按模型双维度）
- 故障复盘与降级事件统计
- 用户行为洞察（意图分布、热门查询、留存率）
- 自动化生成脚本规划

**为什么最后读：** 这份文档是前三份文档的"反馈闭环"。系统跑起来之后，月报数据会反过来驱动数据模型、接口、编排的迭代优化。

## 四、四份文档的逻辑闭环

四份文档不是孤立堆叠，而是一个**完整的工程闭环**：

```
                    ┌─────────────────────────┐
                    │  数据模型（骨架）        │
                    │  unified-data-model     │
                    └────────────┬────────────┘
                                 │ 提供数据契约
                                 ↓
                    ┌─────────────────────────┐
                    │  API 规范（契约）        │
                    │  system-openapi-v1.0    │
                    └────────────┬────────────┘
                                 │ 被编排消费
                                 ↓
                    ┌─────────────────────────┐
                    │  Agent 工作流（大脑）    │
                    │  router-agent-workflow  │
                    └────────────┬────────────┘
                                 │ 产出运行数据
                                 ↓
                    ┌─────────────────────────┐
                    │  运维月报（体检）        │
                    │  ops-monthly-report     │
                    └────────────┬────────────┘
                                 │ 反馈优化建议
                                 │
            ┌────────────────────┴─────────────────────┐
            │                                           │
            ↓                                           ↓
   驱动数据模型迭代              驱动接口与编排优化
```

**这个闭环回答了一个问题：** 一个 AI 系统不是"写完上线就结束"，而是"数据—接口—编排—监控"持续循环演进的有机体。

## 五、与小组其他成员的协作边界

本项目采用「全权负责制」，每位成员独立交付端到端模块。我作为集成端，与其他三位成员的边界如下：

### 5.1 与吴隐（趋势模块）

- **我对她负责：** 提供 `novels` 表写入接口契约、`trend_metrics` 表 Schema、`/api/v1/trend/*` 接口规范
- **她对我负责：** 在 v1.0 截止前交付符合规范的 Mock 接口，正式接口实现后通过集成测试
- **共同所有：** `novels` 表（她负责写入，我负责供其他模块读取的接口）

### 5.2 与吴宸（搜索模块）

- **我对他负责：** 提供 `vector_refs` 表 Schema、`/api/v1/search/*` 接口规范、用户画像中的 `avoid_tags` 字段
- **他对我负责：** 实现语义搜索接口、相似书推荐接口，并支持避雷词过滤
- **协作要点：** 避雷词的**所有权**归集成端（用户画像数据），他作为消费者使用，不直接写入用户表

### 5.3 与武文杰（舆情模块）

- **我对他负责：** 提供 `raw_reviews` / `sentiment_scores` 表 Schema、`/api/v1/sentiment/*` 接口规范
- **他对我负责：** 实现聚合评分、毒舌点评、原始评论列表三个接口
- **协作要点：** 舆情模块是 Router Agent 中**调用频率最高**的下游之一，他需要保证 P95 延迟 ≤ 2000ms

### 5.4 集成端独占职责

以下数据与接口由我独立负责，不与其他成员重叠：

- `user_profiles` 表（用户画像）
- `agent_session_logs` 表（会话日志）
- `token_usage_logs` 表（Token 审计）
- `/api/v1/agent/chat`（中央编排入口）
- `/api/v1/users/*`（用户画像管理）
- `/api/v1/admin/*`（系统运维监控）
- 前端 UI 全部组件（聊天框、大屏、详情页）

## 六、版本管理约定

### 6.1 文档版本规则

- 当前所有文档为 **v1.0**（v1.0 即为首个发布版本，不存在 v0.x 草稿）
- 任何破坏性变更（如接口字段删除、表结构调整）→ 升级主版本号至 v2.0
- 任何非破坏性补充（新增字段、新增接口）→ 升级次版本号至 v1.1、v1.2 ...
- 纯文字描述修订（错别字、说明优化）→ 不升版本，仅在末尾「版本变更记录」标注

### 6.2 V1/V2 并存策略

未来若进入 V2 升级，旧版本接口将**保留 3 个月**作为过渡期：

- V1 接口路径：`/api/v1/...`
- V2 接口路径：`/api/v2/...`
- 数据库表通过新增字段实现兼容，禁止删除旧字段直至下游全部迁移完毕

**苗文昊** · 系统集成与交互体验模块负责人

在本项目中，我选择不去争夺业务模块的"亮点"功能，而是承担集成端这个**看似不出彩、实则决定系统能否真正运转**的角色。我相信一个 AI 系统的优雅，不在于某个模型多强、某个算法多巧，而在于**所有部件能否协同呼吸**。
